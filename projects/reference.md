
## RHEL Workstation Deployment and Cadence EDA Environment Setup

During my internship, I was involved in the deployment, configuration, and standardization of a Linux-based semiconductor design environment across a laboratory consisting of more than 30 workstations. The primary objective was to prepare the laboratory systems for a chip-design workshop in which students would work with industry-standard Electronic Design Automation (EDA) tools and associated RTL-to-design workflows. This required considerably more than a conventional operating-system installation, as each workstation had to be configured as a consistent and functional computing environment capable of supporting the required Cadence toolchain, design libraries, user accounts, permissions, and supporting software.

The initial stage involved installing and configuring Red Hat Enterprise Linux (RHEL) on the laboratory workstations. This included preparing the systems for the required software environment, configuring the operating system, installing necessary dependencies and libraries, and ensuring that the machines could reliably operate the EDA software stack. Since the machines were intended to provide an identical working environment for multiple users, attention was given not only to the installation itself but also to system-level configuration and reproducibility across the workstations.

A significant portion of the work involved the installation and configuration of the Cadence EDA environment. Multiple components of the Cadence software suite were deployed, including GENUS, INCISIVE, FOUNDRY, and ASSURA. The environment was configured to support a Verilog/RTL-oriented chip-design workflow, with the necessary executables, environment variables, paths, libraries, and supporting configuration files established so that the tools could be invoked consistently from the laboratory systems. The deployment also involved verifying that the individual tools were operational rather than treating successful installation of the software packages as the endpoint of the process.

Because the software environment had to function consistently across multiple independently installed machines, a substantial amount of troubleshooting and system-level debugging was required. Problems involving missing dependencies, library compatibility, executable paths, environment variables, permissions, configuration files, and differences between individual workstations had to be identified and resolved. This required examining the interaction between the operating system, installed software, shell environment, filesystem structure, and EDA toolchain rather than treating each issue as an isolated application-level problem.

The workstation configuration also involved establishing a consistent identity and networking environment. Hostnames and user accounts were configured according to the requirements of the laboratory setup, with `/etc/hosts` and other system configuration files modified accordingly. Shell initialization files such as `.cshrc` were configured to establish the appropriate Cadence environment whenever users accessed the systems. These configurations were particularly important for ensuring that students could access the same tools and workflows regardless of which workstation they were assigned.

Another important aspect of the deployment was Linux user, group, and filesystem permission management. In addition to creating and configuring users, I worked with user and group identifiers and, where required by the laboratory's existing configuration, modified GIDs and usernames while accounting for the resulting filesystem ownership and permission implications. Since Linux filesystem permissions are associated with numerical UID/GID identities rather than simply the displayed usernames, changing account identities could result in existing files becoming inaccessible or appearing to belong to different users. Consequently, the deployment required maintaining consistency between account configuration, group membership, file ownership, and permissions so that the Cadence environment and associated design files remained usable.

The process therefore evolved into a broader exercise in system standardization. Rather than simply installing software on individual computers, the objective was to create a reproducible laboratory environment in which the operating system, user configuration, networking, shell environment, permissions, dependencies, and EDA tools all worked together. Each workstation had to be validated as a complete system, and issues encountered on individual machines had to be understood in the context of the larger deployment rather than simply worked around locally.

Alongside the practical deployment work, I also documented the installation and configuration procedures in detail. The documentation developed into a comprehensive technical manual covering the RHEL installation process, system configuration, Cadence installation, environment setup, user and permission management, troubleshooting procedures, and the laboratory workflow. The manual eventually grew to more than 150 pages and was intended to provide a reproducible reference for the complete setup rather than merely serving as an internship report. A separate, considerably shorter report was maintained for formal internship submission.

As the deployment progressed, it became clear that manually reproducing a fully configured workstation across dozens of machines was neither efficient nor sufficiently scalable. Once a workstation had been completely configured and verified as a known-good reference system, the next logical step was to treat that system as a deployment source rather than repeating the entire installation and configuration process independently on every remaining machine.

This led to the next phase of the work: **large-scale workstation replication using Clonezilla**. Instead of rebuilding the RHEL and Cadence environment manually on another set of laboratory machines, I am now using a completely configured and validated workstation as the source system and deploying its contents to approximately 30 additional workstations. The deployment is being performed through a network-based, netbooted Clonezilla environment using multicast for simultaneous distribution, with the source being read directly from the device/disk rather than first creating and distributing a conventional image file. This marks the transition of the project from **manual workstation configuration and standardization to automated, large-scale system deployment**, allowing an already validated laboratory environment to be reproduced across an entire group of machines in a substantially more scalable manner.



Once the reference workstation had been completely configured, validated, and documented, the focus of the work shifted from constructing the laboratory environment to developing a practical method for reproducing that environment at scale. The existence of a known-good workstation containing the complete RHEL operating system, Cadence EDA environment, user configuration, permissions, libraries, and supporting software provided a stable deployment source. The challenge was therefore no longer determining how to configure an individual workstation, but determining how to reliably replicate an entire configured system across a large number of target machines while minimizing manual intervention and ensuring that the resulting systems remained consistent with the validated reference system.

This led to the development and testing of a **network-based Clonezilla deployment workflow using PXE netboot and Clonezilla Live Lite**. The objective was to allow approximately 30 laboratory workstations to boot a Clonezilla environment over the network and receive a complete disk-level deployment from the configured reference workstation. Rather than treating the deployment as a conventional file-based software installation, the intention was to reproduce the workstation at the storage-device level, preserving the operating-system installation, filesystem structure, installed software, configuration files, user environment, permissions, and other system state already present on the source machine. This approach was intended to transform the validated reference workstation into a reproducible deployment source for the remaining laboratory systems.

A major design consideration was the scale of the deployment. Restoring the systems individually would still require substantial operator involvement and would largely defeat the purpose of having established a standardized reference workstation. I therefore explored Clonezilla's **massive-deployment** capabilities, with particular emphasis on multicast-based distribution. The intended workflow was for multiple client machines to PXE boot into Clonezilla, connect to a deployment server, and receive the source disk simultaneously through the network. Multicast was investigated because it allows a single source stream to be distributed to multiple clients rather than transmitting an independent complete copy of the disk to every workstation. This makes the approach substantially more appropriate for deploying a large common workstation environment across an entire laboratory.

The deployment architecture required understanding several layers of the Clonezilla environment rather than treating Clonezilla simply as a graphical disk-cloning utility. The server had to provide the appropriate Clonezilla Live Lite environment and deployment configuration, while the target machines had to obtain that environment through PXE and subsequently execute the correct restoration procedure. The source storage also had to be made available in a form that Clonezilla's massive-deployment mechanisms could consume. This introduced the distinction between conventional Clonezilla image-based restoration and **device-oriented or raw disk deployment**, which became an important part of the investigation.

Instead of initially creating a conventional Clonezilla image archive containing the contents of the reference workstation, I investigated Clonezilla's **device-to-device and raw deployment mechanisms**. The intention was to use the already configured source disk as the basis for deployment and allow Clonezilla to represent the source device through its raw/pseudo-image mechanism where required by the massive-deployment workflow. During this process, Clonezilla generated a `raw-psdo` representation containing the information required to describe the source device and its contents. Understanding the relationship between this pseudo-image representation, the actual source block device, and the target block device became an important part of debugging the deployment process.

The PXE boot process itself was also configured and tested on the target machines. Client systems were configured to boot the Clonezilla environment from the deployment network, allowing the same deployment environment to be loaded without requiring a locally installed operating system. This introduced additional system-level considerations, including firmware configuration and boot security. In particular, systems configured with Secure Boot could reject the Clonezilla PXE boot image because the image was not accepted as an authenticated boot image. Consequently, firmware-level configuration had to be considered as part of the deployment procedure rather than treating PXE booting as an entirely network-side operation.

Once the clients successfully entered Clonezilla, the next challenge was establishing reliable communication between the Clonezilla clients and the deployment server. The Live Lite workflow relies on configuration information being made available to the client, including the instructions required to execute the appropriate `ocs-sr` operation. During testing, clients encountered failures involving `ocs-client-run.conf`, including situations in which the expected configuration file could not be retrieved or was reported as not being assigned. Investigation of the server-side temporary directories also showed that the expected client configuration was not necessarily being generated or exposed in the location anticipated by the client. This indicated that the deployment problem was not limited to disk restoration itself, but also involved the orchestration layer responsible for instructing PXE-booted clients how to perform the restoration.

Another significant issue involved **Linux block-device naming**. The initial deployment command generated by the Clonezilla workflow contained a target device specification such as `sda`. This was problematic because the target laboratory workstations did not necessarily expose their internal storage using the traditional `/dev/sda` naming convention. The target machines used NVMe storage devices, with names such as `/dev/nvme0n1` and `/dev/nvme1n1`. Consequently, a command designed around a fixed `sda` target could not reliably be applied to all target systems.

Attempts to manually substitute an NVMe device name into the server-side command demonstrated an additional complication. Supplying `nvme1n1` where `sda` had previously been specified resulted in errors indicating that the device did not exist in the context in which the command was being executed. This helped expose an important distinction between the **server's view of its own block devices and the client's view of its local storage devices**. A disk name visible on the client cannot simply be assumed to exist in the server's namespace. The server-side Clonezilla process and the client-side `ocs-sr` process operate in different system environments, and the target device must ultimately be resolved within the client operating system where the actual physical disk is present.

This led to a broader investigation of how Clonezilla's massive-deployment workflow constructs and transfers the restoration command. In particular, I examined the generated `ocs-sr` command and the distinction between operations such as `restoredisk` and `multicast_restoredisk`. The client-side command encountered during testing contained parameters similar to:

```bash
ocs-sr -os 20.0.4.184 --ocsroot /tmp/ -1 en_US.UTF-8 \
--batch -g auto -e1 auto -e2 --clone-hidden-data -edio -k0 \
-p poweroff --max-time-to-wait 300 -scr \
--mcast-port 2232 multicast_restoredisk \
"raw-psdo-20260627-195950" sda
```

Examining this command made it possible to separate the actual restoration operation from the surrounding Clonezilla server orchestration. The command identifies the source representation, the restoration mode, network parameters, and the target disk that is ultimately expected to receive the deployment. This provided a more direct way of investigating whether failures were caused by the disk-restoration mechanism itself or by the automated procedure used to deliver the command to the clients.

I therefore planned to isolate the individual components of the deployment rather than continuing to modify the complete automated workflow simultaneously. One approach was to access a Clonezilla client directly through a TTY and execute the relevant `ocs-sr` restoration command manually. This would remove the PXE orchestration and automatic command-generation layers from the immediate experiment and make it possible to verify whether the raw source representation could actually be restored successfully to the client's NVMe device. Once the underlying restoration mechanism was confirmed independently, the automated Live Lite workflow could then be reconstructed around a known-working client-side operation.

The investigation also required distinguishing between **from-device**, **from-image**, and other Clonezilla source modes. The original objective was to avoid unnecessary intermediate image creation and to use the configured reference workstation as the deployment source. However, the behavior of Clonezilla's massive-deployment workflow meant that the source device still had to be represented in a form that could be distributed to the clients. Understanding when Clonezilla expects a conventional image repository, when it can operate on a device source, and how the `raw-psdo` representation fits into this process became necessary for determining the correct architecture rather than simply changing individual command-line arguments.

The deployment method was also evaluated in terms of the available network-distribution mechanisms. Multicast was selected as the primary approach because the same complete workstation environment needs to be distributed to many machines. Broadcast and BitTorrent-style deployment were also considered as alternative distribution mechanisms, particularly in relation to network efficiency and scalability. The intention was not simply to make one workstation clone successfully, but to establish a deployment method that could reasonably be used for the entire laboratory without requiring the source disk to be transmitted independently to every client.

The troubleshooting process therefore evolved into a layered investigation of the complete deployment pipeline:

```text
Reference Workstation
        │
        ▼
Source Disk / Raw Device
        │
        ▼
Clonezilla Live Lite Server
        │
        ├── PXE boot environment
        ├── Client configuration
        ├── Deployment orchestration
        └── Multicast distribution
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Client 1  Client 2  Client N
          │         │         │
          ▼         ▼         ▼
      Local NVMe  Local NVMe  Local NVMe
          │         │         │
          └─────────┴─────────┘
                    │
                    ▼
          Replicated Workstation
```

This approach allowed the problems to be classified into separate categories: PXE and firmware boot configuration, server/client network communication, generation and delivery of client configuration, source-device representation, multicast operation, and target block-device identification. Separating these layers was important because an error at one stage could otherwise appear to be a failure of the disk-cloning mechanism itself.

The ultimate objective of this phase of the internship is therefore to move from a **manually configured and validated reference workstation to a repeatable, network-driven deployment pipeline** capable of reproducing that workstation across the remaining laboratory systems. The desired result is a process in which a target machine can be powered on, PXE boot into the deployment environment, receive the appropriate Clonezilla configuration, identify its own target storage device, participate in the multicast deployment, restore the complete reference disk, and finally reboot or power off automatically. Achieving this would convert the earlier workstation-standardization effort into a scalable provisioning system, significantly reducing the amount of repetitive installation and configuration work required whenever the laboratory needs to deploy or recreate the standardized RHEL and Cadence EDA environment.

The Clonezilla work consequently represents the final stage of the broader deployment problem rather than an independent activity. The earlier phase established **what the standardized workstation should contain**; the current phase is concerned with **how that validated state can be reproduced reliably across many physical machines**. The work has therefore progressed from operating-system installation and EDA environment configuration, through system standardization and validation, to network-based disk replication and automated large-scale deployment.
